# M3 zero-handler-change dialect-switch gate

## Purpose

behind dialect adapters: the shared application source passes both
stable-subset lanes with zero handler code changes, no raw header parsing
exists outside adapters, core/JSX have no htmx dependency, and documentation
never labels beta support as GA. Governed by the [release-gate
standard](../../engineering/release-gates.md) and the [GH-056
issue](../../issues/m3/gh-056-run-the-m3-zero-handler-change-dialect-switch-gate.md).

## Acceptance findings

- **Shared application source passes both stable-subset lanes** — the
  `examples/dual-dialect-fixture/app.ts` produces identical browser behavior
  under htmx 2.0.10 and htmx 4.0.0-beta6 (OOB updates, navigation, error
  negotiation) with the dialect injected only at bootstrap in `server.ts`.
- **No raw header parsing exists outside adapters** — the architecture check
  confines all `HX-*`/`htmx:*` strings to `@bundar/htmx`; the source-diff
  guard catches raw protocol strings in application code.
- **No core/JSX dependency on htmx exists** — core and jsx have zero runtime
  dependencies (ADR-0011); the frozen boundary rules forbid any core→htmx
  or jsx→htmx edge; both are machine-enforced.
- **Documentation never labels beta support as GA** — the htmx4-beta6
  compatibility doc carries explicit `[provisional]` annotations; the
  conformance report disclaims GA; no GA claim appears anywhere in M3
  documentation.
- Raw dialect escape hatches (`rawDialectEvent`, `rawExtension`) are
  explicit branded types carrying approximate-mapping diagnostics for
  auditability — never silent.
- Every skip in the dual-browser lanes has a reason (the htmx error-swap
  DOM divergence is documented; the server-side error check is
  dialect-independent while the main lanes verify dialect-specific DOM
  swaps).

## Frozen migration contract

The dual-dialect fixture freezes the contract that later reference
applications (GH-076, GH-077, GH-082) must satisfy: application code uses
only neutral `@bundar/htmx` exports; dialect selection occurs only in
bootstrap; OOB updates compose via `serializeUpdates`; navigation flows
through `htmxRedirect`/`htmxLocation`; errors flow through
`errorViewResponse`.

## Authorization

## Accepted residual risks

- The htmx 4 beta's error-swap default differs from v2; the fixture uses
  fetch-based error checks while the main lanes verify dialect-specific DOM
  behavior — both documented.
- GA revalidation for htmx 4 is mandatory (M7); nothing in M3 may be read
  as a GA compatibility claim.
- `raw(oobHtml)` for composing OOB markup trusts `serializeUpdates` output
  (documented under the GH-031 boundary).
