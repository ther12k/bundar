# M4 progressive-workflow security gate

## Purpose

M4 closes with maintainers verifying that a representative authenticated,
validated, progressive workflow — the shape every real application will
take — composes the M4 security primitives safely: sessions establish
identity, CSRF tokens bind to it, validation runs identically for ordinary
and enhanced submissions, flash messages render once, errors negotiate
without leaking internals, and authorization never consults HTMX
metadata. Governed by the [release-gate
standard](../../engineering/release-gates.md) and the [GH-069
issue](../../issues/m4/gh-069-run-the-m4-progressive-workflow-security-gate.md).

## Acceptance findings

- **Workflow source is shared across browser modes** —
  `examples/workflow-gate/workflow.ts` serves ordinary browsers
  (Post/Redirect/Get) and enhanced HTMX submissions (fragments) from the
  same handlers; negotiation is per request. The test suite drives both
  lanes against one server per scenario group.
- **Authorization is server-side and independent of HTMX metadata** —
  `requireUser` reads only the session; an enhanced unauthenticated write
  receives the same generic 401 and never mutates state. CSRF integrity
  precedes authorization (a tokenless stranger gets 403, never the
  handler).
- **The synchronizer token binds to the session identity** — page
  renderers issue tokens bound to `session.id` (both the hidden field and
  the `bundar.csrf` cookie); verification enforces cookie/submitted
  equality plus the binding MAC. Cross-origin, missing, tampered, and
  foreign-session tokens all fail closed with a generic 403.
- **A 422 re-render does not rotate the CSRF token** — defect found BY the
  gate and fixed in `csrfMiddleware`: rotation previously ran after every
  verified unsafe request, including 4xx responses that change no state,
  which would have 403'd every retry from a re-rendered form. Rotation now
  applies only to state-changing (non-4xx) responses; the retry-with-same-
  token behavior is unit- and workflow-tested.
- **Validation, flash, and error negotiation compose** — invalid
  submissions re-render with retained safe values at 422; flash messages
  consume exactly once; 401s render a generic document with no protected
  content in both lanes; 404s never leak internals.
- **Dialect adapters thread through the composed workflow** — the same
  create/delete flow passes under htmx 2.0.10 and 4.0.0-beta6 with the
  adapter injected at construction; the application source contains no
  dialect conditionals.
- **The application owns its error boundary** — the reference app wires
  `ErrorBoundary` (GH-020) through `Bun.serve`'s error hook
  (`app.compile()` + `error:`), so thrown `HttpError`s keep their public
  envelope (403 CSRF failures render the envelope, not Bun's default 500
  page).
- No hidden failures: every battery step is exit-0 or the gate stops; the
  full suite (679 tests) has zero skips without documented reason.

## Frozen workflow contract

The reference workflow freezes the composition contract for later
reference applications (GH-076, GH-077) and alpha packaging (GH-071):
sessions via `sessionMiddleware`; CSRF verification scoped to unsafe
routes with page renderers issuing session-bound tokens; validation via
`runFormAction` (Standard Schema in, field-error model out); success via
`action`/`actionResponse` (fragment for enhanced, PRG for ordinary);
errors via `errorViewResponse`; the error boundary wired at serve time.

## Accepted residual risks

- Tokens rotate after every state-changing request, so multi-action
  enhanced sessions must re-render the form region between state changes
  (the PRG document flow does this automatically; enhanced flows re-fetch
  the form region). This is the documented synchronizer contract, not a
  limitation hidden behind example assumptions.
- The workflow uses an in-memory session store and `secure: false`
  cookies for the local/test environment; production deployments must
  supply a durable store and secure cookies (GH-062 documented both).
- Uploads are not part of this workflow's scope (no upload-capable route);
  upload safety is gated by GH-064 and the uploads audit inside the same
  battery.
- GA revalidation for htmx 4 remains mandatory (M7); nothing in M4 may be
  read as a GA compatibility claim.
